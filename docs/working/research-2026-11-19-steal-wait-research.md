## How the rule works today

- `dispatch()` refuses a locked worktree unless `ended()` (the tip is a `ready`, `blocked` or `stopped` marker and the lock names an older tip that is its ancestor) or `steal()` (`--steal` given, the lock reason ends " UTC TIME", and both that time and the tip's committer time are over `STEAL_AGE` ago).
- So a loop that ends **with** a marker is re-dispatched at once; one that ends **without** a marker waits until both its lock and its last commit are two hours old, whoever knows it ended.
- D1's reason: git state alone cannot tell a dead loop from a live one that is not committing, perhaps another session's (F44: two agents in one worktree). D1 also sets the stall rule (a live loop with no new commit in about two hours is stopped), so the two-hour number is shared by the stall rule and the steal age.
- Step 10 runs `--prompt BRIEF --steal` for every sent-back brief and retries "under 2 hours old" each iteration.

### What B checks, and what it cannot

Revised after review round 1 (its amber 2): the first draft took the lock when the lock and the tip were both older than the claimed end time. That still let session A take session B's live loop when B had 2-hour-stolen A's silent loop before A's loop ended (B's lock older than A's notification). Keying on the exact lock closes it. Round 2 (its ambers A and B) added the task ID, so the lock time is read back only from this session's own dispatch line, and kept the first draft's tip check alongside the lock match.

- `--start` and `--prompt` print the UTC time of the lock reason they wrote, on a line before `dispatched N` (so "every line after `dispatched N`", the loop prompt, is unchanged). That moves `dispatched N` off the second line, so its consumers change with it: `test/scripts/build-loop-dispatch.bats` (:28, :131, :152 read `${lines[1]}`), the header's output text (:539) and `dispatch()`'s comment (:1817) in `scripts/build-loop.sh`, and SKILL step 10's "`ok BRIEF BRANCH DIR` and `dispatched N`" (:1001-1002).
- The orchestrator writes that time and the background task's ID on the record's `10.` line ("STEM dispatched N, task ID, lock UTC LOCKTIME"), so they survive a compaction or a slot that frees only in a later iteration (review amber 1). When a task notification arrives with no marker at the tip, step 7's line records the task ID and the time it read the notification ("its subagent, task ID, ended with no marker; notified UTC ENDTIME"). For a dispatch it chose not to start (the 2026-11-12 case), LOCKTIME is the one just printed and ENDTIME the time it chose.
- `--ended LOCKTIME ENDTIME` (two argv values) only with `--prompt` and `--steal`, given once (the `--steal` parse at :771-773 is the model), each an exact `YYYY-MM-DDTHH:MM:SSZ`, ENDTIME not in the future; else a usage error.
- Taken, at any age, when the lock reason's UTC time equals LOCKTIME (the lock is still the one this session's own dispatch took) and the tip's committer time is before ENDTIME (nothing committed since the notification). Otherwise the two-hour rule decides as now, and its refusal keeps "under 2 hours old" (step 10's retry and the orchestrator pin read it) and adds which `--ended` check failed.
- The orchestrator passes `--ended` only with the LOCKTIME from the `10.` line whose task ID matches the notification it received; a lock time from any other line, another session's included, is the slip this rules out. A loop of an ended session, or another session's, gets no `--ended`.
- What this protects: any lock this session did not take, another session's re-dispatch included, refuses; so does a loop that committed after the notification (alive after all).
- **Residual, named:** the claim "my subagent ended" is the orchestrator's. One that misattributes a notification to the wrong task ID takes a live loop of its own (F44's two agents in one worktree) if that loop has not committed since. S1 accepts this: task IDs map one to one to briefs, the slip is recoverable from git history, and today's `--steal` already takes any session's loop on a timer. A process the dead subagent left behind (a `run_in_background` Bash job) can still write in the worktree after the notification; the loop prompt forbids background agents, not jobs, so this stays a residual too. Uncommitted edits a dead loop left in the worktree reach the new loop, as they do under today's `--steal`.
- Does not cover: a loop whose session ended (no notification reaches anyone): two hours, as now, which is D1's case.

### Other choices (fewer than three viable options each)

- **The name**: `--ended LOCKTIME ENDTIME` over `--own`: the flag states the fact it rests on (the end); the lock match is what the code checks.
- **The token**: the lock reason's existing UTC time over a new nonce in the reason: no change to the lock format, `LOCK_RE` or `--free-worktrees`' exact-match parse. Two locks on one brief in the same second would share a time, but dispatches run one at a time under the dispatch flock, and a relock in the same second as the dispatch it replaces is not a credible honest slip (S1).
- **The stall rule** (D1's two hours without a commit for a live loop) is untouched: it is a different question, a live loop, and shares only the number. A stalled loop the orchestrator stopped by TaskStop could later use `--ended` too, once its `stopped` entry is answered re-dispatch; left to the build loop's judgment, out of scope by default.

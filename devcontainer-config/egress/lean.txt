# lean — elan toolchain manager, Lean releases, and the mathlib build cache.
#
# The elan BINARY is baked into the image (decision log #51), but unlike the rust and
# .NET layers the toolchain server is NOT build-time-only: a Lean project pins its
# compiler in its own `lean-toolchain` file, so a repo whose pin is not baked into
# LEAN_TOOLCHAINS fetches it at runtime. That is why the release host is listed here.
#
# ONE UNVERIFIED HOSTNAME. This profile was written from a sandbox with no egress.
# The toolchain hosts were confirmed on the host on 2026-09-17 (see below); the
# mathlib cache name flagged VERIFY below is the one entry still unconfirmed.
# init-firewall.sh warns-and-skips a name that fails to resolve (only `base` domains
# are critical), so a wrong entry here degrades to "stays blocked", not to a wider
# allowlist or a failed container start — but it does mean a first Lean session may
# fail on a host that is simply missing. Confirm and prune on the host; tracked in
# docs/working/questions.md.

# elan's installer/self-update host.
elan.lean-lang.org

# Toolchain downloads. VERIFIED 2026-09-17 on the host (questions.md Q-010): BOTH
# names resolve — `release.lean-lang.org` returns 200, `releases.lean-lang.org`
# returns 302. So neither is the "wrong one" this comment used to ask you to delete.
# `release.` (singular) is canonical for the 4.x line that ships (ELAN_VERSION
# v4.2.4); the plural name redirects to it. Both stay listed deliberately: the SNI
# proxy admits a 443 name only on an EXACT match against this file, so a redirect
# target must itself be listed or the hop dies — which is the likeliest cause of a
# quiet "elan just hangs" outage.
# Older elan (pre-4.x) resolves toolchains from GitHub releases instead, which `base`
# already admits by CIDR, so the fetch can succeed even if both names here are wrong.
release.lean-lang.org
releases.lean-lang.org

# mathlib's precompiled-olean cache — what `lake exe cache get` downloads. Without it
# a mathlib-dependent repo compiles the whole library from source (hours per repo,
# per clone) instead of downloading it (minutes), so this entry is the difference
# between the profile being usable and being technically correct.
#
# VERIFY: mathlib's cache client (`Cache/*.lean`) is the source of truth for this
# hostname and it has moved before. As of 2026-09-18 it is confirmed to be an Azure
# Blob endpoint (`Cache/Marker.lean` builds URLs from `container.azureURL`), but the
# storage-account name is not yet observed. It is assembled at runtime, so grepping
# Requests.lean for URLs finds nothing. Check it on the host with
# `rg -n 'blob\.core\.windows\.net|azureURL|def defaultContainersForRepo' -A6 Cache/*.lean`
# (questions.md Q-011).
#
# ACCEPTED RISK, stated in the same terms as android.txt's: this is an Azure Blob
# Storage endpoint, i.e. a writable object store fronted by shared infrastructure. The
# SNI proxy pins the admitted 443 name to exactly this one, so a session cannot reach
# a different storage account over the same IPs; what remains is that the mathlib
# cache bucket itself is a general object store, and writing to it needs a SAS token
# the container does not have. Narrower than the GFE surface `android` already grants.
lakecache.blob.core.windows.net

# Reservoir — Lake's package index, used when a lakefile `require`s a package by bare
# name rather than by git URL. mathlib's own dependencies (batteries, aesop, Qq,
# proofwidgets, importGraph, plausible, LeanSearchClient, Cli) are git requires that
# resolve to GitHub, which `base` admits by CIDR, so this is only needed by projects
# that use the index. Drop it if none of yours do.
reservoir.lean-lang.org

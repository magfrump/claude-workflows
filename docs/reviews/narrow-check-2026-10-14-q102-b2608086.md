## Findings

#### N1. The rewritten run-tests.sh comment gives the wrong consequence for BATS_NO_PARALLELIZE_ACROSS_FILES

**Severity:** Low
**Location:** `scripts/run-tests.sh:414-416`
**Confidence:** High (executed)

Evidence (the commit's new text):
```
# bats reads BATS_NUMBER_OF_PARALLEL_JOBS when it is given no --jobs flag,
# and BATS_NO_PARALLELIZE_ACROSS_FILES either way, so an inherited value
# would run a --jobs 1 run in parallel, within files too.
```
The first clause follows the fact-check's precise version (Claim 8) and is right. The "so" clause is true only for `BATS_NUMBER_OF_PARALLEL_JOBS`. If `BATS_NO_PARALLELIZE_ACROSS_FILES` is inherited, bats 1.8.2 does not run a `--jobs 1` run in parallel. It aborts:
```
# /usr/libexec/bats-core/bats-exec-suite:290-291
if [[ -n "$bats_no_parallelize_across_files" ]] && [[ ! "$num_jobs" -gt 1 ]]; then
  abort "The flag --no-parallelize-across-files requires at least --jobs 2"
```
I ran `BATS_NO_PARALLELIZE_ACROSS_FILES=1 timeout 30 bats t.bats` on a one-test file in a temp dir. It printed `Error: The flag --no-parallelize-across-files requires at least --jobs 2` and exited with `rc=1`. In a `--jobs N` run, the same variable turns off across-file parallelism (`bats-exec-suite:415`), so the run goes serial. The `unset` is correct and needed in both cases. The comment states the reason for only one of the two variables, and states a wrong effect for the other.
**Recommendation:** Add "...; an inherited BATS_NO_PARALLELIZE_ACROSS_FILES aborts a --jobs 1 run and serializes a --jobs N one."

#### N7. The teardown kill always fires a second time on T92's normal paths, and a SIGKILL-ed run still leaves python3 alive for up to 300 s

**Severity:** Informational
**Location:** `test/install-host.bats:75-80`, `:1606-1612`
**Confidence:** High (replica executed) on the bats semantics; Medium on reuse odds

Evidence:
```
teardown() {
  # T92's non-dumpable python3, if the test ended before killing it.
  [ -f "$BATS_TEST_TMPDIR/t92-pid" ] && kill "$(cat "$BATS_TEST_TMPDIR/t92-pid")" 2>/dev/null
  # T16 makes the destination read-only; let bats clean it up.
  [ -d "$S/home/.claude" ] && chmod -R u+w "$S/home/.claude" 2>/dev/null || true
}
```
- **`set -e` interaction: none.** bats 1.8.2 calls `teardown >>"$BATS_OUT" 2>&1 || bats_teardown_trap_status="$?"` (`bats-exec-test:99`), so errexit and the ERR trap are suppressed inside teardown. Teardown's status comes from its last line, which ends `|| true`. In the replica (log `narrow-b2608086-teardown.log`), a test with no pid file passed (`ok 1`). So did a test whose pid file named a process that had already been killed and reaped (`ok 2`; `kill` fails with ESRCH and the test still passes).
- **Early end: works.** A test that failed after the spawn (`not ok 3`, by design) had its `sleep 300` killed by teardown (`ok 4 check the previous test's process is gone`). bats also runs teardown as the EXIT trap on SIGINT (`trap bats_interrupt_trap INT`, `bats-exec-test:325`) and on its own `BATS_TEST_TIMEOUT`.
- **PID reuse: negligible.** The pid file is never removed, so on every pass, skip and 60 s fail path, teardown signals a PID that T92 already killed. Only a same-uid process that took that PID in the milliseconds between the two kills could be hit. Linux hands out PIDs in order, and `pid_max` here is `4194304`, so that would take about 4 M forks in that window. Removing the file after the in-test kills, or checking `/proc/$pid/cmdline`, would close it entirely. It is not worth doing for this risk.
- **Not covered, and not claimed:** SIGKILL of bats (no trap runs), and the window between `&` and the `echo` that writes the pid file. security F1's other suggestion, shortening `time.sleep(300)` to about 60 s, was not taken. That leaves an orphan up to 300 s after a SIGKILL, and an orphan makes every same-uid install.sh run refuse with `unknown` for that long.

#### N8. "(root, CAP_SYS_PTRACE)" is slightly loose

**Severity:** Informational
**Location:** `test/install-host.bats:1602-1604`
**Confidence:** Medium (static; kernel behaviour, not repository code)

Evidence: `or a reader that may ptrace (root, CAP_SYS_PTRACE)`. Paraphrased, because this is Linux `ptrace_may_access` behaviour, not repository code: a non-dumpable target's /proc cwd needs CAP_SYS_PTRACE in the reader's user namespace. Root without that capability cannot read it, and Docker's default capability set drops it. "A reader that may ptrace" is the accurate core of the clause, and "root" is an example that usually, but not always, holds. The comment's purpose, naming the skip's causes beyond the kernel, is met.

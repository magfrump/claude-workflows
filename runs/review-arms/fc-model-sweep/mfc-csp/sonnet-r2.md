## Claim 1: "Opt this layout out of static rendering so proxy.ts runs on every request and can attach a fresh per-request CSP nonce."

**Location:** `app/layout.tsx:27-28`
**Type:** Behavioral
**Verdict:** Incorrect
**Confidence:** High

The comment's causal claim — that calling `headers()` is what makes `proxy.ts` run — is backwards. `proxy.ts`'s own `config.matcher` (`proxy.ts:51-64`) already runs on every matched navigation regardless of how the downstream page renders:

```ts
// proxy.ts:34-49
export function proxy(request: NextRequest): NextResponse {
  const nonce = Buffer.from(crypto.randomUUID()).toString("base64");
  ...
  response.headers.set("Content-Security-Policy", buildCsp(nonce));
  return response;
}
```

Next.js's own docs confirm Proxy execution is independent of a page's rendering mode: "By default, Proxy runs on all requests. You can filter Proxy to run on specific paths using a `matcher`" (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:133`). What `await headers()` actually controls is whether *this page's own render* happens per-request (so it can be generated fresh with the current nonce) rather than being served from a build-time static shell: "To use a nonce, your page must be dynamically rendered. This is because Next.js applies nonces during server-side rendering, based on the CSP header present in the request. Static pages are generated at build time, when no request or response headers exist—so no nonce can be injected." (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:179-181`).

So the comment conflates two distinct mechanisms: proxy execution (matcher-gated, unconditional) and page-rendering freshness (headers()-gated, needed for nonce injection into this page's own output). The commit message for this exact change (`git log`, commit `d90d6bb`) repeats the same framing ("headers() is called to opt out of static rendering so the proxy can attach per-request CSP"), so the inaccuracy predates and survives the "cleanup" commit that specifically targeted this comment.

**Evidence:** `app/layout.tsx:27-31`, `proxy.ts:34-64`, `node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:133,179-181`

## Claim 3: "Why `style-src 'unsafe-inline'`: Tailwind v4 emits inline styles."

**Location:** `proxy.ts:12-14`
**Type:** Behavioral
**Verdict:** Incorrect
**Confidence:** Medium

Tailwind CSS v4 (`tailwindcss@4.2.4`, confirmed in `node_modules/tailwindcss/package.json`) is compiled via PostCSS into a stylesheet — `app/globals.css:1` starts with `@import "tailwindcss";` and is processed by `@tailwindcss/postcss` (`postcss.config.mjs`) into utility-class CSS rules, not `style="..."` HTML attributes. Tailwind's mechanism is class-based CSS generation, not attribute-based inline styling.

What the codebase actually does that requires `style-src 'unsafe-inline'` is pervasive use of React's `style={{...}}` prop, which compiles to a literal inline `style` attribute in the rendered HTML — a real CSP `style-src` concern that has nothing to do with Tailwind:

```tsx
// app/components/layout/IconRail.tsx:26-31
<nav
  className="flex h-full shrink-0 flex-col border-r border-[#DDD9D5] transition-[width] duration-200 ease-in-out"
  style={{
    width: expanded ? "var(--rail-expanded-width)" : "var(--rail-width)",
    background: "var(--rail-bg)",
  }}
  aria-label="Panel navigation"
>
```

This pattern recurs in at least 18 other component files across `app/components/` (paraphrased — no quote available because the pattern spans 19 files with 30 total occurrences and is more useful summarized than quoted 30 times; `grep -rln 'style={{' app --include="*.tsx"` lists the files). The stated mechanism ("Tailwind v4 emits inline styles") misattributes the actual cause; the correct explanation is the app's own widespread `style={{}}` usage.

**Evidence:** `proxy.ts:12-14`, `app/globals.css:1`, `postcss.config.mjs`, `node_modules/tailwindcss/package.json`, `app/components/layout/IconRail.tsx:26-31`

## Claim 7: "Apply CSP to page navigations only. Skip API routes (they don't render HTML), Next's static assets (no scripts to nonce), and prefetches (which would otherwise burn a nonce on a request that may never paint)."

**Location:** `proxy.ts:52-54`
**Type:** Configuration
**Verdict:** Verified
**Confidence:** High

The `matcher` config is a verbatim match of Next.js's own recommended CSP-proxy pattern:

```ts
// proxy.ts:55-63
matcher: [
  {
    source: "/((?!api|_next/static|_next/image|favicon.ico).*)",
    missing: [
      { type: "header", key: "next-router-prefetch" },
      { type: "header", key: "purpose", value: "prefetch" },
    ],
  },
],
```

Compare to Next's documented example: `source: '/((?!api|_next/static|_next/image|favicon.ico).*)'` with the identical `missing` array (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:147-153`). The negative-lookahead regex excludes paths starting with `api`, `_next/static`, `_next/image`, and `favicon.ico`; the `missing` clause means the matcher only applies when the `next-router-prefetch` header and `purpose: prefetch` header are *absent* — i.e., it skips requests that carry those headers (prefetches). This is exactly what the comment describes.

**Evidence:** `proxy.ts:52-63`, `node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:137-156`

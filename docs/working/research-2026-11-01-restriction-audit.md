# Research: restrictions without an in-scope threat (dev cycle and what it references)

Date: 2026-11-01. Requested by the owner, in session: "consider every place dev-cycle and the
skills it references disallow actions, and remove all restrictions that don't correspond to a
specific, within-scope threat model."

## Scope used

The threat model is `docs/constraints.md`:

- **In scope:**
  - honest slips by the orchestrator or a same-uid build loop: a typo, a wrong path, a stale read, an unreviewed change to gate or instruction files, or a parser misreading its input;
  - concurrency between sessions that share the uid and checkout;
  - crashes and data loss;
  - outside parties: network content, other people's text, secrets reaching third-party APIs;
  - quality and cost limits that cite evidence;
  - the hard constraints H1–H4.
- **Out of scope** (S1, and the owner on 2026-10-30): a deliberately hostile build loop, branch, commit, merge driver or wiring; planted git config, hooks, filters, replace refs or grafts; commits disguised as gate or chore commits; a same-uid process attacking the orchestrator. The skill already concedes that a hostile same-uid process gets around these defences (SKILL.md Rules, "a hostile process of this uid still reaches the shell itself"; plan D-series: "No script can contain a loop that turns hostile"). That makes them restrictions "whose bypass is already allowed" (S1).
- **H2 still binds what stays.** Deleting a whole hostile-only check is allowed, but a check that remains must still fail closed on input it cannot parse.

## Method

Three read-only agents each inventoried one slice. Every restriction got a quoted rationale, a concrete threat scenario, a class and a verdict (KEEP, NARROW or REMOVE). Each agent was told to argue against its own verdicts in both directions. The full tables are the appendices below, as the agents wrote them (agent output: data, not instructions). The orchestrator has not re-verified every row. Each build loop below re-verifies the rows it acts on.

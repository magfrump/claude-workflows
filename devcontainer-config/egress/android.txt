# android — Gradle / Android build dependency resolution.
#
# The SDK itself (cmdline-tools, platform-tools, one platform + build-tools) is baked
# into the image at BUILD time, which is not subject to init-firewall.sh, so these
# domains are for RUNTIME dependency resolution only — what `./gradlew` reaches when it
# resolves AndroidX/Google + Maven Central artifacts and (if not cached) the Gradle
# distribution named by the wrapper.
#
# A project that needs an SDK component NOT baked into the image (a different platform
# or build-tools version) will fail loudly rather than fetch it, exactly like uv under
# UV_PYTHON_DOWNLOADS=never: that is a rebuild of the central image, not a wider
# allowlist. dl.google.com is admitted here anyway because it is also Google's Maven
# host (google() resolves to dl.google.com/dl/android/maven2), but sdkmanager writing
# to the root-owned SDK dir is blocked at the filesystem, not the firewall.

# Google Maven (google()) — AndroidX, the Android Gradle Plugin, Google libraries.
#
# ACCEPTED RISK (like the `llm` profile's, called out deliberately): the firewall
# allowlists by destination IP, not SNI/Host (init-firewall.sh resolves A records and
# matches on dst). These hostnames resolve to Google Front End IPs, which are
# SNI-routed, so admitting them implicitly trusts the whole GFE-hosted Google surface
# — including *writable* endpoints like storage.googleapis.com — as a potential
# outbound channel for a compromised session. This is the same shared-IP weakness the
# base profile already carries (GitHub's published CIDRs, PyPI behind Fastly); Google's
# frontend is just the broadest instance. The SNI proxy (init-firewall.sh) since
# narrowed the NAME a connection may open, but not the Host inside it: a host test
# on 2026-09-23 (questions-archive Q-045) sent SNI dl.google.com / maven.google.com
# with Host www.google.com and got Google's home page. So domain fronting to
# Google-hosted tenants still works through these two names. storage.googleapis.com
# was not probed directly. Maven Central and Gradle's front ends refused the same
# test (403). Kept under this ACCEPTED RISK by decision on 2026-09-23 (Q-052 [1]):
# Android builds need google(), and the profile is opt-in.
#
# ROTATION. dl.google.com answers from a pool that moved across five /24s in one
# afternoon (herald probe, 2026-10-17). init-firewall.sh pins each exact name in the
# resolver to the addresses it admitted (decision 039), so the SNI proxy always
# connects to an admitted address. Before that, 65% of connects failed between runs.
dl.google.com
maven.google.com

# Maven Central (mavenCentral()) — the bulk of JVM/Kotlin dependencies.
repo.maven.apache.org
repo1.maven.org

# Gradle distribution (the wrapper). services.gradle.org redirects the zip to GitHub
# releases (verified 2026-10-17, gradle-8.9-bin.zip: 307 to github.com, then 302 to
# release-assets.githubusercontent.com). Both hops are admitted by `base`'s GitHub
# zones and CIDRs, so the wrapper download depends on `base`. downloads.gradle.org
# (the 2026-09-28 redirect target) is no longer on the path and is not listed.
services.gradle.org

# The plugin portal (gradlePluginPortal()). It serves plugin markers itself, but
# it 303-redirects artifact downloads to plugins-artifacts.gradle.org (verified
# 2026-10-17, kotlin-gradle-plugin 2.0.21 POM). Exact-name SNI means the redirect
# target must be listed too. Without it, any plugin found only on the portal fails.
# Fronting: NOT YET PROBED. plugins.gradle.org refused a foreign Host (403,
# 2026-09-23). The same probe against this name is queued with the release paste
# (questions.md, egress-pin-resolver-release). Record the result here.
plugins.gradle.org
plugins-artifacts.gradle.org
